# Proposal: ingesta-pdf-password — unlock password-protected PDF statements

> SDD propose artifact. Hybrid store — mirror of Engram topic `sdd/ingesta-pdf-password/proposal`.
> No `explore.md` preceded this change; the codebase map came from the orchestrator and was re-verified
> against the sources cited below. This is a PROPOSAL: intent, scope, approach, risk, rollback, slicing —
> not the spec, not the design, not code.

## Intent

**Problem.** Chilean banks routinely email statements encrypted with the holder's RUT. Today such a file is
a dead end: `PdfTextExtractor.extract()` calls `getDocument({data, disableFontFace, useSystemFonts})`
(`pdf-text-extractor.ts:48-59`) with no `password`, and its `catch` at `:60-65` flattens **every** load
failure into `PdfInvalidoError`. A perfectly valid, merely locked statement is reported to the user as a
corrupt file. The user has no path forward and no accurate diagnosis — the product silently lies about why
the upload failed.

**Why now.** The preview → commit flow (US-057) is the primary ingestion path in the web app and is stable.
The fix is additive and touches no persistence: `pdfjs-dist@6.2.108` already supports
`DocumentInitParameters.password?: string` (`types/src/display/api.d.ts:38`) and already distinguishes
`PasswordException` with `PasswordResponses.NEED_PASSWORD | INCORRECT_PASSWORD`
(`types/src/shared/util.d.ts:330-338`). We are not building capability — we are stopping the code from
discarding information pdfjs already hands us.

**Success looks like.** A user uploads a locked `.pdf` through the web app, is told *specifically* that the
file is password-protected, types the password once, and completes preview → commit. The password never
reaches the database, the logs, or an error message. An unlocked PDF behaves exactly as it does today.

## Scope

### In scope

- New domain error for a password-protected PDF, in `domain/errors/`, shaped like `pdf-invalido.error.ts` /
  `pdf-sin-texto.error.ts` (ADR-005; `Result<T,E>`, never throw — ADR-015).
- `PdfTextExtractor` accepts an optional password, passes it to `getDocument`, and **discriminates**
  `PasswordException` from a genuine load failure instead of collapsing both into `PdfInvalidoError`.
- Threading that password through **all three** PDF stages. There is no single interception point: each of
  `pdfjs-bank-detector.service.ts:44`, `pdfjs-structure-validator.service.ts:66` and
  `pdfjs-transaction-normalizer.service.ts:74` instantiates its **own** `PdfTextExtractor` (`:27`, `:27`,
  `:35`) and re-parses the buffer — an accepted design documented at
  `pdfjs-transaction-normalizer.service.ts:20-26`. One password must reach three re-parses, via their three
  ports and three wrapper use cases.
- `EjecutarPipelineIngestaInput` (`ejecutar-pipeline-ingesta.use-case.ts:29-31`) carries the password; the
  new error joins `EjecutarPipelineIngestaError` (`:52-61`).
- HTTP contract on **preview** and **commit**: an optional `password` text field on the existing multipart
  request. Multer already lets extra text fields through — commit reads `edits` this exact way
  (`ingesta.routes.ts:175-178`, schema `ingesta-commit.schema.ts:26-34`). Contract-first per ADR-011/012:
  Zod schemas updated, `openapi.json` re-emitted, `packages/api-client` regenerated via `contract:sync`.
- Error → status mapping in `aHttpError` and `aCommitHttpError` (`ingesta.routes.ts:385-416`, `:342-378`).
  Both end in `const _exhaustive: never = error` (`:413`, `:375`) — **the new error breaks compilation in
  both until handled. That is the safety net, not an obstacle.**
- **No `Ingesta` row on a locked/wrong-password file.** This is a validation error, not a failed ingesta.
  It needs an explicit carve-out: `commit-ingesta.use-case.ts:210-216` today calls `registrarFallo(...)` on
  **any** pipeline failure. Three wrong password attempts must not produce three rows in the user's history.
- Reactive web UX in `SubirCartola.tsx`: **no password field is rendered by default.** The user uploads
  normally; only when the API reports "protected" does the UI reveal a password prompt and retry with the
  `File` object still held in memory — the user never re-picks the file.
- The web client keeps the password in **ephemeral React state across preview → commit** (commit re-parses
  the file from scratch, and nothing is stored server-side). Typed once. **Never** `localStorage` /
  `sessionStorage`.
- A **new encrypted PDF fixture**, generated by a committed script alongside the existing generators in
  `apps/api/test/fixtures/pdf/` (e.g. `generar-bci-cartola-montos-grandes-test.ts`). None of the 8 current
  fixtures carries `/Encrypt`, and `pdf-text-extractor.spec.ts` covers corrupt and text-less PDFs but not
  encrypted ones.

### Out of scope (explicit non-goals)

- **Encrypted `.xlsx` — NOT supported.** ExcelJS cannot decrypt OOXML workbooks; its README documents only
  `worksheet.protect()`, which is *write-side sheet protection*, not read-side decryption. Supporting it
  means a new binary-parsing dependency, which collides head-on with ADR-007 (SheetJS rejected over
  unpatched CVEs) and requires its own ADR. Out.
- **Mobile — NOT in this change.** `apps/mobile` ships no UI here. The HTTP contract MUST be designed so
  mobile can adopt it later with **zero server change** (ADR-024/ADR-026/ADR-038 keep the domain in the
  backend). Follow-up change.
- **The password is NEVER persisted.** No DB column, no encrypted-at-rest storage, no session cache, no
  migration. It travels in the request, opens the PDF, and is discarded — which keeps this change entirely
  clear of ADR-013 storage decisions. It MUST also never reach logs (ADR-033 Pino redaction) or any error
  message, in line with the existing amount/PII scrubbing rule.
- **NOT** a general secrets-handling mechanism, retry-limit policy, or rate limiter for password attempts.
- **NOT** changing the unlocked-PDF path, the Excel pipeline, normalization, or any money logic.

## Capabilities

### New Capabilities

- None.

### Modified Capabilities

- `pdf-ingesta`: the extraction stage gains password-protected PDF handling. Delta spec adds roughly two
  requirements after `PDF-05` — **`PDF-06`** (a protected PDF is reported as protected, never as invalid;
  a correct password unlocks all three stages; a wrong password is reported distinctly) and **`PDF-07`**
  (the password is never persisted, logged, echoed, or recorded as an `Ingesta`). `PDF-01`'s current
  "corrupt PDF → `PdfInvalidoError`" scenario needs narrowing so an encrypted PDF no longer falls under it.
  Exact IDs and Given/When/Then are the spec phase's call.

## Approach

Thread one optional value inward, and stop throwing away a distinction pdfjs already makes.

1. **Domain first** (ADR-005 ordering): the new error, with `Result.fail` semantics, no throw.
2. **Extractor:** pass `password` to `getDocument`; in the `catch`, inspect the exception for the pdfjs
   password signal and return the new error instead of `PdfInvalidoError`. Design must decide how to detect
   it robustly across the dynamic-ESM-import boundary (`instanceof` on a dynamically imported class is
   fragile; the `name`/`code` fields are the safer read).
3. **Application:** optional password on the three ports, their three use cases, and the shared pipeline
   input; the new error joins the pipeline error union.
4. **Infrastructure:** the three adapters forward it to their own extractor; the two routes read the
   optional multipart field exactly as commit reads `edits`; both `_exhaustive` guards force the mapping.
5. **Contract:** Zod schemas → `openapi.json` → `packages/api-client` via `contract:sync`.
6. **Web:** reactive reveal-on-demand password prompt + ephemeral state across preview → commit.

Strict TDD throughout (`strict_tdd: true`, `pnpm api test`, ADR-016): RED-GREEN-REFACTOR, starting from a
failing extractor test against the new encrypted fixture.

**KISS/YAGNI posture.** No new dependency, no new pattern, no migration. The optional field mirrors an
existing precedent (`edits`) rather than inventing a mechanism. Nothing speculative ships: no attempt
counter, no password policy, no mobile plumbing.

## Open design questions (for `sdd-design` — deliberately NOT decided here)

1. **Port signature shape.** Do the three ports each take `password?: string`, or does a small carrier
   object / value object travel instead? ISP says don't widen three signatures for one optional field;
   YAGNI says don't introduce an abstraction for a single value with one caller. Real tension, real
   tradeoff — design decides with the code in front of it.
2. **The deprecated one-shot `POST /ingestas`** (`ingesta.routes.ts:90-117`). Does it get the capability at
   all, or only preview + commit? The user's actual flow is preview → commit; teaching a deprecated
   endpoint a new trick may be dead code on arrival.
3. **One error or two.** `ArchivoProtegidoError` with a discriminator, versus distinct `NEED_PASSWORD` and
   `INCORRECT_PASSWORD` errors — and whether the distinction is surfaced to the client at all. The classic
   password-oracle objection is weak here (it is the user's own file, uploaded in their own session), but
   it must be stated and dismissed explicitly, not assumed away.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Password leaks into a log, error message, or Sentry-style payload | Med | ADR-033 redaction + explicit spec requirement (`PDF-07`) + a test asserting the password appears in no log/response |
| Password leaks into browser storage or a browser-persisted form field | Med | Ephemeral React state only; no `localStorage`/`sessionStorage`; design specifies the input's autocomplete posture |
| Three extractors drift — one stage forgets the password and re-locks mid-pipeline | Med | Threading all three is in scope by design; a test unlocks the **full** pipeline end to end, not just the extractor |
| Password-exception detection is fragile across the dynamic ESM import boundary | Med | Design pins the detection strategy; the encrypted fixture makes it testable and regression-proof |
| Locked-file retries pollute ingesta history | Med | Explicit carve-out at `commit-ingesta.use-case.ts:210-216`, with its own test |
| Contract drift — `openapi.json` / `api-client` not regenerated | Low | CI drift-check already guards this (`openapi:check`); `contract:sync` in the task list |
| Scope creep into encrypted `.xlsx` or mobile | Low | Both are named non-goals; `.xlsx` additionally requires a new ADR (ADR-007) |
| Change spans backend + contract + web in one PR | High | Slicing below; see Review Workload Forecast |

## Rollback plan

Low-risk by construction: **no Prisma migration, no schema change, no data backfill, nothing persisted.**
The feature is purely additive — an absent password means byte-identical behavior to today.

- Any slice reverts with `git revert` of its merge commit. No data repair, no state to unwind.
- Backend and web are independently revertible: reverting the web slice leaves an unused optional API field;
  reverting the backend slice makes the web password prompt receive the old `PdfInvalidoError` and show the
  current (wrong-but-existing) error. Neither breaks unlocked-PDF ingestion.
- If reverting a contract slice, re-run `contract:sync` so `openapi.json` and `packages/api-client` return
  to the committed pre-change state; CI's drift-check catches a half-revert.
- Emergency partial rollback: reverting only the web slice disables the capability from a user's point of
  view without touching the API.

## Slicing strategy

Strict TDD per slice (`pnpm api test`), each slice green and independently revertible.

- **Slice 1 — domain + extractor + fixture.** New error, encrypted fixture + generator, `PdfTextExtractor`
  password support and `PasswordException` discrimination. Self-contained; no contract change.
- **Slice 2 — thread it inward.** Three ports, three adapters, three use cases, pipeline input + error
  union, and the commit no-FALLIDA carve-out. Resolves design question 1.
- **Slice 3 — HTTP contract.** Optional field on preview + commit, both `_exhaustive` mappers, Zod schemas,
  `contract:sync` (`openapi.json` + `packages/api-client`). Resolves design questions 2 and 3.
- **Slice 4 — web reactive UX.** `client.ts`, the two hooks, `SubirCartola.tsx` state machine
  (`idle → previsualizando → preview-listo → committing → exito/error` plus the protected branch), tests.

## Dependencies

- `pdfjs-dist@6.2.108` — already installed; password support and `PasswordResponses` verified in its shipped
  type declarations. **No new dependency.**
- No new ADR is required: this change lives inside ADR-009's PDF pipeline. If design concludes a new
  dependency is needed after all, that decision escalates to an ADR before any code.

## Success criteria

- [ ] A locked PDF uploaded to preview returns a *protected* error — never `PdfInvalidoError`.
- [ ] The correct password completes preview **and** commit, all three PDF stages unlocked, typed once.
- [ ] A wrong password is reported as such and produces **no** `Ingesta` row.
- [ ] The password appears in no log, no error message, no response body, no DB column, no browser storage.
- [ ] An unlocked PDF and every `.xlsx` path behave exactly as before (existing suites green, unchanged).
- [ ] The web upload form renders no password field until the API says the file is protected.
- [ ] `pnpm api test`, `pnpm web test`, `tsc --noEmit`, and the `openapi.json` drift-check are green.
